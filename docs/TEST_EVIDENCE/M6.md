## G1 — real -O0/-O1/-O2 C builds with truthful evidence

`c_opt_worker.py` (analyzer image) builds the immutable snapshot source per level
with recorded verbatim flags (`-O{N} -g -no-pie -fno-omit-frame-pointer` — no user
flags anywhere), emitting IR/assembly/object/executable/symbols with digests,
sizes and per-step durations; clang version ("Ubuntu clang version 18.1.3
(1ubuntu1)") and target triple recorded; remarks availability honest.

- **Independent oracle** (`test_opt_independent_host_clang_oracle`): host
  clang-18 with the same recorded flags reproduces the container's function
  symbol inventory exactly at O0 and O2.
- **Real transformation** (`test_opt_transformation_and_distinct_levels`): a
  called 4-iteration loop keeps its compare/jump form (`jge`) at -O0; at -O2 the
  function is inlined away and main contains a single `movl $6, %esi`. Honest
  side-note recorded: an UNCALLED static function is eliminated at EVERY level
  (global DCE), and source-level constants like `2*21` fold during IR generation
  even at -O0 — neither is claimed as an optimization-level effect.
- Static assembly is labeled "NOT an executed-instruction count" in the UI and
  API docs. No pass-level attribution beyond compiler-reported data.

## G2 — Python: no fake levels

Benchmarks expose exactly one Python level (`py312`); the UI and tests assert
`"O0"/"O2" not in levels` for Python (`test_bench_python_no_fake_levels`); the
Compare page states "Python has no LLVM -O levels". Bytecode-stage comparison is
version-pinned (CPython 3.12.3) and reuses the M2 analysis artifacts; runtime
specialization is documented as a runtime-only phenomenon (not measured here).

## G3 — five pair specs, both pipelines, verified expectations

`sandbox/fixtures/pairs/manifest.json` — add / conditional / recursion /
arraysum / sort, each C+Python with matched inputs and `expected_stdout`
verified with HOST clang-18 -O2 and host CPython 3.12.3 (reproducibility script:
`scripts/dev/m6_verify_pairs.sh`). The verification itself caught a real policy
violation: the original sort checksum overflowed signed 64-bit in C (undefined
behavior) while Python continued with big ints — both sides now use a modulo
checksum. `test_compare_all_five_pairs_match` runs all five pairs through the
REAL M4 execution pipeline (10 container executions) and asserts both sides
match the expected output with exit 0.

## G4 — benchmark science (real measurements)

`bench_worker.py` (runtime image) on UNINSTRUMENTED binaries: 2 warmups excluded,
≥5 timed samples, per-sample wall + CPU, checksum-per-run (all identical),
median/min/max/stdev from stored raw samples, environment provenance (CPU model,
kernel, cgroup cpu.max/memory.max — the container's own throttled limits, 0.5
CPU / 256 MB, recorded so numbers are read as container-throttled). Sampled
medians < 5 ms carry `resolution_warning` (the pair fixtures run ~0.4–0.6 ms in
the container — flagged, not embellished). Traced-vs-untraced separation: M4/M5
execution records (instrumented) keep their own durations; benchmark numbers are
never mixed with them.

## Known limitations

1. Benchmark numbers are container-throttled (0.5 CPU) and single-machine;
   comparisons across levels are same-environment only. No universal
   "C is N× faster" claims are made anywhere.
2. Sub-5 ms medians (pair fixtures) are flagged `resolution_warning`; the M7
   suite should use scaled workloads for serious timing.
3. Pass-level optimization attribution is limited to compiler-emitted remarks;
   `-Rpass`-style attribution is marked available/unavailable per build.
4. IR/asm excerpts are bounded (24 KB view / 64 KB stored); larger artifacts
   are flagged truncated.
